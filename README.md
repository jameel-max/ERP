# نظام إدارة المشغل والتجار — رويال فروت (Royal Fruit Packhouse ERP)

نظام ERP متكامل لإدارة مشغل فرز وتوضيب الفواكه، مبني على **Python + Django**، واجهة **عربية RTL متجاوبة** (Bootstrap 5 RTL)، رسوم **Chart.js**، أكواد **QR/SSCC**، وتوليد **PDF/Excel** للفواتير والتقارير. جميع الحسابات المالية تُنفَّذ بـ `Decimal` بالدينار الأردني (3 خانات، `ROUND_HALF_UP`)، والمنطقة الزمنية **Asia/Amman**.

---

## 1) المتطلبات

- Python 3.12 أو أحدث
- (اختياري) PostgreSQL 14+ — النظام يعمل أيضاً بـ SQLite افتراضياً
- متصفح حديث

## 2) التثبيت

```powershell
# 1. إنشاء بيئة افتراضية وتفعيلها
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# 2. تثبيت الحزم
pip install -r requirements.txt

# 3. إنشاء جداول قاعدة البيانات
python manage.py migrate

# 4. تهيئة النظام (حساب المالك الوحيد + الإعدادات — بدون بيانات تجريبية)
python manage.py init_system
```

### التشغيل السريع (بعد التثبيت)

بضغطة واحدة بعد تفعيل البيئة الافتراضية:

```powershell
.\scripts\quick_start.bat
```

أو مباشرة:

```powershell
python scripts\quick_start.py
```

### حسابا الإدارة (بعد `init_system`)

| المستخدم | كلمة المرور | الصلاحية |
| --- | --- | --- |
| `ammar` | `ammar123` | مالك النظام — صلاحيات كاملة (كل العمليات والموافقات والتفريغ) |
| `salah` | `salah123` | مالك النظام — نفس الصلاحيات الكاملة تماماً |

`init_system` يُنشئ **حسابَي إدارة فقط** (`ammar` و `salah`) بصلاحيات متطابقة وكاملة، ولا يُنشئ أي بيانات تجريبية. لتوليد بيانات عرض فقط: `python manage.py init_system --demo`.

> **مهم:** غيّر كلمتي المرور الافتراضيتين فوراً في الإنتاج. (بيانات الدخول لا تظهر في شاشة تسجيل الدخول.)

### العمل دون إنترنت

المكتبات الأمامية (Bootstrap، Bootstrap Icons، Chart.js، خط Cairo) تُقدَّم محلياً من `static/vendor`، لذا يعمل النظام دون إنترنت. لتحديثها لاحقاً: `python scripts/fetch_frontend_assets.py`.

## 3-ب) النشر الإنتاجي

راجع الدليل الكامل: **`deploy/README_DEPLOY_AR.md`**. الخلاصة:

```powershell
Copy-Item deploy\env.example .env   # ثم عدّل SECRET_KEY و DJANGO_DEBUG=False والنطاقات
.\scripts\serve_production.ps1      # هجرات + تجميع الملفات الساكنة + خادم Waitress
```

- **الخادم:** Waitress (Windows/Linux). **الملفات الساكنة:** WhiteNoise.
- **وكيل عكسي/HTTPS:** `deploy/nginx.conf.example`. **كخدمة Linux:** `deploy/royal-fruit.service`.

يُقرأ أيضاً تلقائياً من ملف `.env` إن وُجد (بدون مكتبات إضافية).

```powershell
Copy-Item deploy\env.example .env  # قالب جاهز للتعديل
```

| المتغير | الافتراضي | الوصف |
| --- | --- | --- |
| `SECRET_KEY` | مفتاح تطويري | **يجب تغييره إلى قيمة عشوائية في الإنتاج** |
| `DJANGO_DEBUG` | `True` | اجعله `False` في الإنتاج |
| `DJANGO_ALLOWED_HOSTS` | `*` | النطاقات المسموحة مفصولة بفواصل (مثال: `erp.example.com,127.0.0.1`) |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | فارغ | أصول موثوقة للـ CSRF في الإنتاج (`https://erp.example.com`) |
| `DB_ENGINE` | `sqlite` | `sqlite` أو `postgresql` |
| `DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT` | (اختياري) | مطلوبة فقط عند استخدام PostgreSQL |
| `SERVER_HOST`/`SERVER_PORT`/`SERVER_THREADS` | `0.0.0.0`/`8000`/`8` | لخادم Waitress الإنتاجي |
| `SECURE_SSL_REDIRECT` | `True` | يُقصد به عند `DEBUG=False`؛ ضع `False` لو الخادم خلف وكيل يعكس HTTPS |
| `SECURE_HSTS_SECONDS` | `31536000` | مدة HSTS بالثواني (افتراضي سنة) |
| `DB_NAME` | `royal_fruit_db` | اسم قاعدة بيانات PostgreSQL |
| `DB_USER` / `DB_PASSWORD` | `postgres` | بيانات الدخول |
| `DB_HOST` / `DB_PORT` | `localhost` / `5432` | عنوان ومنفذ الخادم |

### مثال تشغيل على PostgreSQL

```powershell
$env:DB_ENGINE="postgresql"
$env:DB_NAME="royal_fruit"
$env:DB_USER="royal"
$env:DB_PASSWORD="********"
python manage.py migrate
python manage.py init_system

```

## 5) النسخ الاحتياطي والاستعادة

```powershell
# نسخة احتياطية (SQLite: نسخ الملف / PostgreSQL: dumpdata JSON)
python manage.py backup_db

# مجلد مخصص
python manage.py backup_db --output-dir backups
```

تُحفظ النسخ في مجلد `backups/` مع ملف `RESTORE_INSTRUCTIONS.md`.

**الاستعادة (SQLite):**
1. أوقف الخادم.
2. انسخ ملف النسخة الاحتياطية إلى جذر المشروع وأعد تسميته `db.sqlite3`.
3. `python manage.py migrate`

**نسخة يومية تلقائية:** أنشئ مهمة في Windows Task Scheduler تشغّل `python manage.py backup_db` يومياً.

## 10) الحوكمة المالية والعُقَد (ملخص)

- **الترقيم:** الدفعة `سنة-رقم تسلسلي` (2026-0143)، الطبلية `الدفعة-P03`، الموضّبة `...-P03-XL`، الفاتورة `سنة-رمز التاجر-رقم`.
- **الدقة:** كل المبالغ `Decimal` (3 خانات، `ROUND_HALF_UP`)، ومجموع بنود الفاتورة يطابق إجماليها.
- **الذرّية:** العمليات المالية والمخزنية المترابطة داخل معاملة واحدة (تنجح كلها أو تُلغى كلها).
- **منع التكرار:** قيود فريدة ومعرفات للمصادر تمنع تكرار القيد عند إعادة الإرسال.
- **الحذف المنفرد والمراقب:** يمكن حذف أي سجل «بشكل منفرد» من زر الحذف في صفحات القوائم/التفاصيل عبر شاشة تأكيد تعرض السجلات المرتبطة وأثرها (يُحذف معه / يُبقى مع إلغاء الربط / يمنع الحذف). تُسجَّل كل عملية حذف في سجل التدقيق باسم المستخدم. وإذا كان السجل مرتبطاً بسجلات محميّة (`PROTECT`) يُرفض الحذف برسالة عربية واضحة تشرح ما يجب حذفه أولاً — بلا أي خطأ 500. (راجع البند 10-هـ.)
- **الحقول الحرجة وغير الحرجة:** قابلة للتعديل من صفحة «إعدادات النظام» (البند خامساً)؛ الحقل الحرج الناقص يمنع الحفظ، وغير الحرج يُنشئ إشعاراً برابط تعديل مباشر.
- **خيار نزول البضاعة على طبالي وعدد الطبالي:** في نموذج استلام السيارة خيار «نزلت البضاعة من السيارة على طبالي» (مُفعَّل افتراضياً). عند إلغائه (بضاعة تصل بكمات بلا طبالي) **لا يُخصم وزن الطبالي من الصافي المحسوب**، لكن العمال يرتّبون البضاعة على طبالي في المشغل فعلياً، **فتبقى الطبالي تُولَّد للتخزين والتوضيب**. وعدد الطبالي **يُحسب تلقائياً** من حقل «عدد الصناديق على الطبلية» (افتراضي 80): `عدد الطبالي = تقريب لأعلى (عدد الصناديق ÷ عدد الصناديق على الطبلية)`، ويُوزَّع كل سيخ/سيخ. عند تفعيل الخيار يُخصم وزن الطبالي (10 كغ لكل طبلية من إعدادات النظام). ويُعرض وسم «بضاعة بكمات — لا يُخصم وزن الطبالي» في صفحة السيارة وقوائم السيارات.
- **توزيع الطبالي على الأسياخ تلقائياً:** عند اختيار البراد تُفلتر قائمة الأسياخ على أسياخ ذلك البراد فقط، وتُخفى الأسياخ الممتلئة. ويبدأ التوزيع من السيخ المختار (ويُختار تلقائياً أول سيخ متاح إن لم تختَر)، وعند امتلائه ينتقل للسيخ التالي، ولا يستخدم سيخاً ممتلئاً (المشغول ≥ السعة) حتى يصبح فيه مكان. وإن لم تكفِ سعة أسياخ البراد يُرفض الحفظ برسالة عربية واضحة. وكل طبلية تُسجَّل على السيخ الذي وُضعت فيه فعلاً في بطاقتها وسجل حركتها. **سعة السيخ:** إن تُركت فارغة تُحسب تلقائياً = تقريب لأعلى (سعة البراد ÷ عدد أسياخه)، فإن كانت سعة البراد نفسها فارغة فالسيخ غير محدود (لا امتلاء ولا انتقال). ويمكن دائماً تحديد سعة سيخ صراحةً لتتجاوز المحسوب.
- **رقابة عدد المقاسات مقابل الطبالي:** كل سطر ناتج توضيب = طبلية موضبة واحدة بوزنها ورمز QR الخاص، ويمنع النظام حفظ أسطر نواتج أكثر من عدد طبالي الاستلام المسحوبة من البراد في الجلسة (يشمل إعادة إرسال النموذج)، ويعرض عدّاد «الأسطر / الطبالي المتاحة» في الصفحة.
- **لا يُفترض أي سعر أو مصروف داخل الشيفرة — كل الأسعار في صفحة «إعدادات النظام»:** أي سعر أو تكلفة تشغيلية يستخدمها النظام في أي شاشة تُقرأ من إعدادات النظام ولا تُكتب ثابتة في الكود. وتشمل: **سعر الكيلو الموضب المجمد الافتراضي لكل طريقة توضيب على حدة** (حقلان مستقلان: **مكينة** و**يدوي** — عند إنشاء فاتورة لتاجر بلا سعر توضيب ساري يُختار السعر الافتراضي الموافق لطريقة التوضيب المحددة، مع تنبيه واضح، ثم يُجمَّد في `packing_rate_snapshot`؛ وسعر التاجر الساري يتقدّم عليه)، **أجرة تبريد الطبلية الموضبة اليومية**، **سعر الصرف الافتراضي مقابل الدينار** (القيمة المبدئية في نموذج الشحنة التجارية ودفعاتها)، **سعر ساعة العامل الافتراضي وبدل المواصلات اليومي** (يُستخدمان إذا كانت الورشة بلا سعر محدد)، **ساعات العمل الافتراضية اليومية**، **وزن الصندوق الفارغ ووزن الطبلية الفارغة**، وحد سماح فرق الوزن %، ومدة تنبيه FIFO. فمثلاً سعر الكيلو الموضب المجمد الظاهر في صفحة الفاتورة `/invoices/<رقم>/` يأتي أصلاً من إعدادات النظام (أو من سعر التاجر) ولا يوجد سعر مكتوب في القالب ولا في الشيفرة.
- **نقل الطبالي بالسحب والإفلات من خريطة البرادات والأسياخ:** في صفحة «البرادات والأسياخ» يمكن سحب بطاقة أي طبلية (استلام أو موضبة) وإفلاتها داخل السيخ المستهدف فتُنقل فوراً، وتُحدَّث عدّادات الإشغال بعد إعادة تحميل الصفحة. على الحاسوب بالفأرة، وعلى الهاتف بضغطة مطوّلة على البطاقة ثم تحريك الإصبع إلى السيخ. الفحص كله في الخادم: النقل يتطلب صلاحية مالك/مدير/محاسب (غير ذلك يُرفض بـ 403)، ويُرفض نقل إلى سيخ ممتلئ أو براد ممتلئ برسالة عربية واضحة، والإفلات على السيخ الحالي لا يُنفّذ أي حركة. نقل الطبلية الموضبة يُغلق فترة التبريد الحالية ويفتح فترة جديدة بنوع «نقل» فلا تُفقد الأيام المحتسبة سابقاً. (نقطتا النقل: `pallets/<id>/move/` و`packing/pallets/<id>/move/`.)
- **إنشاء بيان تسليم فارغ؟** لا.
- **تسليم الفارغ للمزرعة أو بيعه لمنظمة:** قسم مستقل «تسليم الفارغ» يوثّق خروج الصناديق الفارغة المجموعة في المشغل بعد تفريغ البضاعة الخام: **إرجاع إلى المزرعة** بلا مقابل مالي، أو **بيع لمنظمة/جهة أخرى** بمقابل. لكل جهة مستلمة سجل (مزرعة أو منظمة) مع المسؤول والهاتف. لا يمكن تسليم أكثر من الفارغ المتاح فعلاً (الناتج عن التفريغ ناقص ما سُلِّم سابقاً) — والفحص ذرّي داخل قفل صفوف. البيع: يُثبَّت الإجمالي (الكمية × سعر الصندوق) ويُقيَّد في الخزينة عند الاعتماد بطريقة قبض نقدية/بنكية، وخيار «على الحساب» يبقى بلا قيد خزينة، والقيد يحدث **مرة واحدة فقط** (الأمر المعتمد لا يُعاد اعتماده ولا يُعدَّل). هذا الرصيد منفصل تماماً عن عهدة التجار وعن مخزون صناديق الشركة.
- **إضافة أكثر من صنف تغليف لناتج توضيب واحد وخصمه من التاجر:** في نموذج «إدخال نواتج التوضيب بالمقاسات والهالك» يمكن لكل مقاس ناتج إضافة **أكثر من صنف تغليف عادي**، وكل صنف من **مجموعة تغليف مختلفة** (صندوق، ورق تغليف، ستيكر، شبك حماية، فواصل...). القائمة مقسّمة إلى مجموعات (`optgroup`) مع سعر كل صنف، ويُعرض إجمالي الخصم مباشرة. **السعر يُجمَّد لحظة الحفظ** (لقطة `unit_price_snapshot`) فلا تتغير الفاتورة لو غُيّر سعر الصنف لاحقاً، وتُجمَع قيمة كل الأصناف في قيد واحد على التاجر لكل جلسة، ثم تُرحَّل إلى فاتورته كبند «خدمات إضافية» **مرة واحدة فقط** (الترحيل قابل للتكرار بلا مضاعفة). أوزان أصناف التغليف لا تدخل في حساب الرندمان أو الوزن الموضب — تُخصم قيمتها مالياً فقط. (الجداول: `packing.PackingOutputPackagingItem` و`packing.PackingSessionPackagingCharge`.)
- **تمييز التجار بصرياً:** خريطة البرادات تُلوّن بضاعة كل تاجر بلون ثابت مميز مع مفتاح ألوان.
- **تصنيفات المصاريف قابلة للإدارة والإضافة السريعة:** صفحة مستقلة «تصنيفات المصاريف» (`/expense-categories/`) تعرض كل التصنيفات مع عدد المصاريف وإجماليها لكل تصنيف، وتتيح الإضافة والتعديل والحذف المنفرد. وفي نموذج تسجيل المصروف يوجد زر **«+»** جانب قائمة التصنيف يقسّم قسماً مدمجاً لإضافة تصنيف جديد **دون مغادرة الصفحة**، فيُضاف ويُختار في القائمة فوراً. إن أُدخل اسم تصنيف موجود مسبقاً يُعاد التصنيف الموجود ويُختار تلقائياً بدل رفض العملية (لا خطأ 500 ولا تكرار). التصنيف المرتبط بمصاريف مسجّلة محميّ من الحذف الصامت (`PROTECT`). وتُنشأ عند `init_system` **12 تصنيفاً افتراضياً جاهزاً** (كهرباء وماء، إيجار، محروقات، صيانة وإصلاح، نقل وشحن، مواد تعبئة وتغليف، أجور عمالة، رسوم حكومية ورخص، اتصالات وإنترنت، مصاريف إدارية ومكتبية، نظافة ومستلزمات، مصاريف أخرى) قابلة للتعديل والحذف.
- **قسم مستقل «الموظفون (رواتب شهرية)» — لا دخل له بالورش:** قسم منفصل تماماً عن «الورش والعمالة» (`/employees/`) للموظفين ذوي **الراتب الشهري الثابت** (محاسب، حارس، سائق، إداري...). لكل موظف بطاقة (الاسم، المسمى، الهاتف، الراتب الشهري، تاريخ التعيين، الحالة) وسجل رواتب شهري مستقل. تسجيل الراتب يكون **«مستحقاً»** (لا يمسّ الخزينة) أو **«مدفوعاً فعلاً»** (يخصم من الخزينة **مرة واحدة فقط** عند الصرف)، ولا يُسمح بتسجيل راتب الشهر نفسه مرتين لنفس الموظف (قيد فريد `employee+year+month`). حذف قيد راتب مسجّل بخطأ يعيد المبلغ للخزينة ويُوثَّق في سجل التدقيق. **رواتب الموظفين لا تدخل إطلاقاً في كلفة الكيلوغرام الموضب ولا في فاتورة التاجر** (القاعدة 4) — ويوجد تقرير رواتب شهري (`/employees/salary-report/`) يجمع المستحق والمدفوع لكل شهر ولكل موظف. الجداول: `labor.Employee` و`labor.EmployeeSalaryPayment`، والخدمة: `labor.services.EmployeeService`.
- **عودة الموضب للتبريد (خدمة يومية):** الطبلية الموضبة يمكن إدخالها إلى البراد/السيخ مرة أخرى بعد التوضيب (حالة «في تبريد المشغل»)، ويُحتسب لكل طبلية عدد أيام بقائها في البراد × الأجرة اليومية المعتمدة، ويظهر ذلك في «كشف التبريد اليومي» وفي بند مستقل داخل الفاتورة (`cooling_subtotal`). إخراج الطبلية يوقف الاحتساب ويحفظ الأيام المسجّلة، وكل إدخال/إخراج/نقل يُسجَّل في سجل موثّق.
- **ملصق الطبلية = رمز QR فقط:** صفحة طباعة الملصق (طبلية الاستلام أو الطبلية الموضبة، وملصقات السيارة دفعة واحدة) تُطبع رمز QR وحده بلا أي معلومات مكتوبة، ومسحه يفتح **بطاقة الطبلية** (صفحة HTML) التي تعرض كل بياناتها: التاجر ونوع البضاعة والمقاس والوزن والصناديق، والطبلية الأصلية والدفعة والسيارة والسائق، والبراد والسيخ، وفترات التبريد وأيامها. الرابط المُشفَّر يُبنى من إعداد **«عنوان السيرفر لروابط مسح QR»** (مثل `http://192.168.1.50:8000`) ليعمل المسح من هواتف الشبكة المحلية دون إنترنت، وإن تُرك فارغاً يُستخدم عنوان الصفحة الحالي.

## 10-ب) إعدادات تحتاج اعتماد صاحب المنشأة

يطبّق النظام قاعدة "نقص البيانات": أي قيمة غير محددة تبقى إعداداً قابلاً للتغيير ويُمنع اعتماد العملية المتأثرة فقط، ولا يُخترع أي رقم. السياسات التالية تحتاج اعتماداً:

- حد السماح لفرق وزن التوضيب (للتأثير على اعتماد الهالك/الفرق).
- سعات البرادات والأسياخ المعتمدة (وحدتها).
- مدة التخزين المعتمدة لتنبيه الأقدم أولاً (FIFO).
- أجرة تبريد الطبلية الموضبة اليومية (الافتراضي 0 = لا تُحتسب أي أجرة حتى اعتماد السعر).
- سعر الكيلو الموضب المجمد الافتراضي **لكل طريقة (مكينة/يدوي) على حدة**، وسعر ساعة العامل وبدل المواصلات، وساعات العمل الافتراضية، وسعر الصرف الافتراضي — كلها في صفحة إعدادات النظام.
- أسعار التوضيب لكل تاجر وطريقة، وأسعار خصم الصناديق.
- سياسة الاعتراف بالمصروف والفترة التي يخصها.

## 10-ج) موارد التغليف والصناديق الواردة من المزرعة

قسمان منفصلان تماماً في المخزون والتقارير:

1. **موارد التغليف (قسم الشركة):** صفحة مستقلة تنشئ مجموعات (مثل: الصناديق، ورق التغليف، الستيكرات)، وكل مجموعة تحتوي أصنافها ومقاساتها ووزنها الفارغ وسعر خصمها ورصيدها. هذه هي الصناديق والمواد المستخدمة في توضيب البضاعة، وتبقى مرتبطة بمنظومة التوضيب وعهدة التجار. تظهر في القائمة الجانبية باسم **«موارد التغليف»**.

2. **الصناديق الواردة من المزرعة (قسم مستقل):** لكل سيارة يُسجَّل نوع الصندوق الوارد، وعدد الصناديق الواردة مع البضاعة الخام، وعدد الصناديق الفارغة الناتجة عن التفريغ. تُحتسب أرصدة هذا القسم من سجلات السيارات وحدها، **ولا تمسّ إطلاقاً** رصيد صناديق الشركة (`BoxType.company_stock`) ولا أرصدة عهدة التجار. تظهر في القائمة الجانبية باسم **«الصناديق الواردة من المزرعة»**، ومن صفحة تفاصيل السيارة يمكن تسجيل صناديقها مباشرة.

**مصدر «نوع الصناديق» في استلام السيارة:** حقل «نوع الصناديق \*» في نموذج استلام السيارة يسحب أنواعه من **أنواع الصناديق الواردة من المزرعة** (`FarmBoxType`) فقط، وليس من صناديق الشركة المستخدمة في توضيب البضاعة (`BoxType`). أما آخرون في `BoxType` فلا يظهرون في الاستلام إطلاقاً.

**نسبة الصناديق للتاجر:** كل سجل صناديق مزرعة مرتبط بالتاجر صاحب السيارة (`FarmBoxRecord.trader`)، ويُشتق تلقائياً من السيارة عند الحفظ فلا يمكن نسب صناديق سيارة إلى تاجر آخر. تعرض اللوحة ملخصاً لكل تاجر (عدد سياراته، إجمالي الوارد، إجمالي الفارغ الناتج) مع فلترة حسب التاجر، إضافةً إلى قسم خاص في صفحة تفاصيل التاجر.

كل سيارة لها سجل واحد فقط لصناديق المزرعة (OneToOne)؛ وإعادة الفتح تُحوِّل إلى تعديل السجل القائم بدل تكراره.

**عدد الفارغ الناتج = عدد الصناديق الواردة (افتراضياً):** بما أن الصناديق التي تصل مع البضاعة الخام هي نفسها التي تصبح فارغة بعد التفريغ، يُعبَّأ حقل «عدد الفارغ الناتج» تلقائياً بنفس «عدد الصناديق الواردة» (عبر مربّع اختيار «نفس عدد الصناديق الواردة» مع مزامنة فورية أثناء الكتابة)، ويمكن إلغاء المزامنة وتعديل الرقم يدوياً عند نقصٍ أو تلفٍ في الصناديق. ونتيجةً لذلك تتطابق إجماليات «الصناديق الواردة» و«الصناديق الفارغة الناتجة» افتراضياً. وعلى مستوى الخادم، إن تُرك الحقل فارغاً يُضبط تلقائياً مساوياً لعدد الوارد.

## 10-د) منع الإدخال المكرر وأخطاء 500

كل نماذج الإضافة/التعديل التي تحتوي حقولاً فريدة (مثل: اسم/رمز البراد، رمز التاجر، اسم مجموعة التغليف، رقم دفعة السيارة، سيخ البراد) تعرض الآن **رسالة خطأ عربية واضحة داخل النموذج** عند إدخال قيمة مكررة، بدل تعطّل الصفحة بخطأ 500 من قاعدة البيانات.

- طبقة الحماية على مستوى الخادم عبر الدالة المساعدة `core.utils.save_form_transactionally` التي تلتقط `IntegrityError` وتحوّله إلى خطأ نموذج (`non_field_errors`).
- طبقة حماية في المتصفح (`templates/base.html`) تمنع **الإرسال المزدوج** للنموذج (نقر الزر مرتين) الذي قد يسبّب تصادماً على القيود الفريدة، خصوصاً مع زمن استجابة الشبكة.

## 10-هـ) الحذف المنفرد لأي سجل في النظام

يوفّر النظام زر حذف منفرد (أيقونة سلة المهملات) في صفحات القوائم والتفاصيل لكل الكيانات الرئيسية: التجار، أنواع البضاعة، أنواع الصناديق، مجموعات التغليف، البرادات، الأسياخ، السيارات (دفعات الاستلام)، الطبالي، سجل درجات الحرارة، أرصدة وحركات صناديق التجار، الصناديق الواردة من المزرعة، الفواتير وبنودها، جلسات التوضيب ونواتجها والهالك والطبالي الموضبة وفترات تبريدها وبيانات التسليم، الورش وسجلات أيام العمالة، الحسابات والخزينة وتصنيفات المصاريف والمصاريف والشيكات وسندات القبض والتحويلات الداخلية وقيود كشوف التجار، والإشعارات، وشحنات الاستيراد والتصدير وتكاليفها ودفعاتها ومستنداتها، والصور المرفقة بأي سجل.

- **شاشة تأكيد واضحة:** قبل الحذف تظهر صفحة تعرض السجل المطلوب وسجلاتٍ مرتبطة به وجدولاً بالأثر: «يُحذف معه تلقائياً» (CASCADE)، أو «يُبقى مع إلغاء الربط» (SET_NULL)، أو «يمنع الحذف» (PROTECT).
- **حماية القيود:** إذا كان السجل مرتبطاً بسجلات محميّة (مثل قيد مالي أو مخزني معتمد) يُرفض الحذف برسالة عربية تشرح ما يجب حذفه أولاً — لا تُكسر سلامة الدفاتر ولا يظهر خطأ 500.
- **سجل تدقيق:** كل حذف يُسجَّل في «سجل التدقيق» باسم المستخدم المنفِّذ ووقت العملية.
- **الصلاحيات:** الحذف متاح للمالك/المدير فقط (`manager_required`)، ويُقيَّد بنوع الكيانات المسجّلة في `core/delete_registry.py` (لا تُحذف حسابات المستخدمين ولا إعدادات النظام ولا سجل التدقيق).
- **التقنية:** مسار واحد عام `delete/<app_label>/<model_name>/<pk>/` مع قالب `core/confirm_delete.html` وزر قابل لإعادة الاستخدام `core/_delete_button.html`.

## 10-و) قسم الاستيراد والتصدير (شحنات حقيقية)

قسم كامل في القائمة الجانبية («الاستيراد والتصدير» ← «شحنات الاستيراد والتصدير») يغطّي دورة التجارة الخارجية من الشراء حتى الربح، ويعمل دون إنترنت. كل المبالغ تُحوَّل إلى الدينار الأردني (JOD) بسعر صرف يُدخَل يدوياً.

1. **تسجيل الشحنات (`/trade/` و`/trade/create/`):** رقم شحنة تلقائي (`IMP-YYYY-0001` للاستيراد و`EXP-YYYY-0001` للتصدير)، النوع (استيراد/تصدير)، المورد/العميل وبلده، وصف البضاعة (وربط اختياري بأنواع البضاعة في النظام)، الكمية ووحدتها، سعر الوحدة، العملة (دينار/دولار/يورو/جنيه/درهم/ريال/ليرة/يوان...) وسعر الصرف، والمنشأ والوجهة.
2. **متابعة الشحنات:** حالة الشحنة (قيد التحضير، في الطريق، وصلت، تم التخليص، تم التسليم، مغلقة، ملغاة) وتواريخ الطلب والمغادرة والوصول المتوقع والفعلي، مع تحديث سريع للحالة من شاشة التفاصيل.
3. **حساب التكاليف:** قيمة البضاعة (الكمية × سعر الوحدة × سعر الصرف) + تكاليف إضافية مُفصَّلة (النقل/الشحن، الجمارك، التخليص، التأمين، التخزين/الميناء، أخرى) بعملات مختلفة مع سعر صرف لكل بند، ثم **إجمالي التكلفة**.
4. **متابعة الأوراق:** تسجيل المستندات (فاتورة تجارية، شهادة منشأ، بيان جمركي، قائمة تعبئة، بوليصة شحن، شهادة صحية نباتية، أخرى) برقمها وتاريخ إصدارها وحالة استلام الأصل.
5. **تسجيل الدفعات:** مدفوع للمورد (استيراد) أو مقبوض من العميل (تصدير) بالمبلغ والعملة وسعر الصرف وتاريخ الدفعة وطريقتها ومرجعها، مع حساب **الرصيد المتبقي** مع الطرف الآخر تلقائياً.
6. **مطابقة الكميات:** الكمية المشحونة مقابل الكمية الواصلة والكمية التالفة، واستخراج **النقص** تلقائياً مع تنبيه بصري للشحنات التي فيها نقص.
7. **معرفة الربح:** الإيراد (قيمة البيع النهائية، أو قيمة البضاعة لشحنات التصدير) ناقص إجمالي التكلفة = **الربح** وهامش الربح.

صفحة القائمة تعرض مؤشرات: عدد الشحنات، الشحنات في الطريق، إجمالي التكلفة، إجمالي الربح المحقق، المتبقي للموردين، المتبقي على العملاء، وعدد الشحنات التي فيها نقص.

**التقنية:** تطبيق `trade` (نماذج `TradeShipment`, `ShipmentCost`, `ShipmentPayment`, `ShipmentDocument`، ترحيل `trade/migrations/0001_initial.py`)، والحسابات في خصائص النموذج (`goods_value_jod`, `total_cost_jod`, `revenue_jod`, `profit_jod`, `counterparty_balance_jod`, `shortage_quantity`). كل عمليات الإضافة/التعديل ذرّية (`transaction.atomic`) وتُسجَّل في سجل التدقيق، وكل الحذف عبر السجل الموحّد `core/delete_registry.py` مع شاشة تأكيد. الصلاحيات: التسجيل والتعديل والدفعات للمحاسب/المدير/المالك، والحذف للمالك/المدير.

> ملاحظة: دفعات الشحنات سجل فرعي داخل قسم الاستيراد/التصدير ولا تُرحَّل تلقائياً إلى دفتر الخزينة العامة، تجنّباً للازدواج مع دفعات الخزينة — تُسجَّل المراجع (رقم الحوالة/الشيك) للربط اليدوي عند الحاجة.

## 10-ز) إرفاق الصور (عدة صور لكل سجل)

يمكن إرفاق **صورة أو أكثر** بأي سجل من السجلات المدعومة، وعرضها كمعرض مصغّرات مع تكبير عند النقر، وحذف أي صورة بشكل منفرد.

- **الشاشات المدعومة حالياً:** شحنات الاستيراد والتصدير، دفعات/سيارات الاستلام، الطبالي، التجار، جلسات التوضيب، الفواتير. أي شاشة تفاصيل أخرى تُضاف بسطر واحد فقط: `{% attachments object %}` بعد `{% load attachments_tags %}`.
- **الإرفاق أثناء التسجيل:** في شاشة «تسجيل شحنة استيراد/تصدير جديدة» (وكذلك التعديل) يمكن اختيار صورة أو أكثر مباشرةً قبل الحفظ، فتُرفَق بالشحنة تلقائياً بعد حفظها، مع وصف اختياري للصور.
- **الرفع المتعدد:** في نموذج الرفع يمكن تحديد **عدة صور معاً** من نافذة اختيار الملفات، مع وصف اختياري يُطبَّق على كل صور الدفعة الواحدة.
- **العرض والتكبير:** شبكة مصغّرات، وعند النقر تُفتح الصورة بالحجم الكامل في نافذة معتمة (Lightbox) — بدون أي مكتبة خارجية (يعمل دون إنترنت).
- **الحذف المنفرد:** زر (×) على كل صورة يحذفها بعد تأكيد، ويحذف ملفها من التخزين أيضاً. الصور المرفقة مُدرَجة كذلك في «الحذف المنفرد» العام.
- **القيود (برسائل عربية واضحة):** الأنواع المسموحة JPG/PNG/WEBP/GIF، وحجم كل صورة حتى 8 ميجابايت، وبحد أقصى 30 صورة لكل سجل. الملفات غير الصالحة أو التي تتجاوز الحد تُتجاهَل تلقائياً دون كسر العملية أو إظهار خطأ 500.
- **الصلاحيات:** الرفع والحذف للمحاسب والمدير والمالك؛ و«المشاهد» يرى الصور فقط دون تعديل. كل رفع/حذف يُسجَّل في «سجل التدقيق» (UPLOAD_ATTACHMENTS / DELETE_ATTACHMENT).
- **التقنية:** موديل `core.Attachment` بعلاقة عامة (`ContentType` + `GenericForeignKey`) ليخدم أي موديل في النظام، والوسم `{% attachments object %}` في `core/templatetags/attachments_tags.py`، والقالب `templates/core/_attachments.html`، والإعدادات في `core/attachments.py`، والمسارات `attachments/upload/<app_label>/<model_name>/<pk>/` و`attachments/<pk>/delete/`. تُحفظ الملفات في `media/attachments/<app>/<model>/<record_id>/`، وتُخدَم في وضع التطوير عبر `MEDIA_URL`.
